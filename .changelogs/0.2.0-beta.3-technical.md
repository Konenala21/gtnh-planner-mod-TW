# 0.2.0-beta.3: under the hood

Code links are pinned to [f35169c](https://github.com/jackwrichards/gtnh-planner-mod/tree/f35169ca19132f8cff9342cd65b76e08cb475b3e). ## The rule

A machine count has one of three rules. Any: the plan picks it. Up to N: the machines run as hard as the rest of the plan lets them and never above N. Exactly N: the old pin, N machines flat out, any gap shown as a forced flow. [`PinRule`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/PinRule.java#L33) reads it for a card and for a shared machine. Saves write `machineCountExact` only on an Exactly card, so every count set before reads as Up to and a plan with no Exactly saves byte for byte as before. A custom rate card is always Exactly. A fluid tank has no count ([`Node.isMachineCountFixed`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/Node.java#L71)).

## Into the solver

[`SolveInput.of`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/SolveInput.java#L225) turns an Up to count into a one-machine pool with that capacity and no fixed count, and a set shared machine into a pool marked Exactly or Up to ([`PoolIn`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/SolveInput.java#L155)). Exactly stays the fixed count it always was.

Two pieces sit on top of the existing stages:

- **The guard** ([`UpTo.prepareGuard`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/UpTo.java#L71), run by [`GuardStage`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/stages/GuardStage.java)): on a network that only Up to pools anchor, the open gates are shut, so no forced flow makes up for what the machines cannot do. They slow down instead. An Exactly pin on the same network opens them again, as before. Drawers and Up to buffers count as the player's own ends.
- **The push** ([`UpTo.push`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/UpTo.java#L155), [`PushStage`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/stages/PushStage.java)): a pool's level is its machine time over its capacity ([`levelOf`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/UpTo.java#L101)). Stage A runs everything as hard as it can: the largest sum of levels, old Build's first stage. Stage B shares out what is left fairly: progressive max-min over the levels, each round freezing the pools that cannot rise and holding their bands as rows. The max-min vector over a convex set is unique, so the answer does not depend on the order the simplex takes.

## The read-out

[`UpToRead.of`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/UpToRead.java#L142) says for every Up to pool how far it got and why: FULL, BOTTLENECK (with what the line wants), STARVED (the short input), CLOGGED (the full output), UNUSED or LIMITED. It asks small capability and disposal LPs, at most 96 a solve. A starved machine whose maker is itself short blames upstream, so the bottleneck lands on the machine that sets the pace.

[`findLoops`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/data/flowchart/balancer/UpToRead.java#L197) brings back old Build's dead loops and clog locks: a STARVED pool blames the pools making its short input, a CLOGGED or UNUSED one those taking its full output, and a strongly connected part of that graph where every member is STARVED is a dead loop, every member CLOGGED or UNUSED a clog lock. The board gives each one a notice and lights its cards and wires ([`Loops`](https://github.com/jackwrichards/gtnh-planner-mod/blob/f35169ca19132f8cff9342cd65b76e08cb475b3e/src/main/java/com/gtnhplanner/ui/Loops.java#L44)).

## EU per item

The website's rate key has had a fifth setting since September: EU, the energy each unit cost. The rebuilt board only ported the four clocks. It is back in [7ecc171](https://github.com/jackwrichards/gtnh-planner-mod/commit/7ecc171e).

It is a reading, not a rate. [`Fmt.euEach`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/theme/Fmt.java#L116) is a card's draw times 20 over a port's flow a second. Both grow with the machine count, so the count cancels. The figure depends on the recipe, the tier and the overclock and never on what is set: a regular overclock doubles it per tier and a perfect one leaves it flat. Nothing reaches the solver.

- The key steps /t, /s, /min, /hr, EU ([`stepRateKey`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/BoardSession.java#L195)). On EU `rateUnit()` stays the clock it was on, so typed and wheeled rates, wires, drawers and the overview's boxes keep it.
- A port reads [`BoardSession.euEach`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/BoardSession.java#L207): its card's average draw ([`averagePower`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/BoardSession.java#L213), a crop's per harvester) over the port's flow. EU ports, power cards and steam machines keep their rate. [`drawRail`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/card/RecipeCard.java#L1273) draws it with [`CardPaint.energyWords`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/card/CardPaint.java#L163) in the website's amber, an input a step quieter.
- The overview's inputs and outputs read the plan's average draw (`Totals.euAverage`, [summed here](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/BoardSession.java#L2859)) over each line's flow ([`OverviewRail`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/OverviewRail.java#L564)). That is the whole chain's cost. As on the website a run's energy is never split between its outputs: GTNH has no fair price to split it by.
- A port's hover has an Energy row whatever the key is on ([`BoardScreen`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/BoardScreen.java#L1245)).
- It uses three figures ([`Fmt.brief`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/main/java/com/gtnhplanner/ui/theme/Fmt.java#L69)) so "307k EU/Item" fits a card's row whole.

Checked in the GregTech dev game: an HV EBF making 1 rutile dust a second runs 53.3 machines at 25.6k EU/t, so rutile reads 512k EU/Item on the card and in the overview. [`FmtTest`](https://github.com/jackwrichards/gtnh-planner-mod/blob/7ecc171ec9e5b9c89bbc37c41ac5dc71f5010d0e/src/test/java/com/gtnhplanner/ui/FmtTest.java#L31) pins the sum.
